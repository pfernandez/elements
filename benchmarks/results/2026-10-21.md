# Fresh descriptions, observers, memory and startup — 2026-10-21

Elements is competitive with the memoized React table when it retains unchanged
row descriptions. Rebuilding those descriptions reveals a substantial update
cost. Independent observers scale well in the focused probe; repeatedly selecting
fresh observations of one shared observer produces quadratic notification work.
These findings identify optimization targets without requiring an API change.

[Raw samples, environment and source/bundle hashes](./2026-10-21.json) and
[reproduction instructions](../README.md) accompany this local investigation.
The runtime is unchanged from `99bad11`; this work adds benchmark fixtures only.

## Table interactions

Median total interaction time in milliseconds, including browser rendering:

| Workload | Elements retained | Elements fresh | React memoized | React fresh |
| --- | ---: | ---: | ---: | ---: |
| Create 1,000 rows | 51.9 | 50.8 | 47.3 | 46.8 |
| Update every tenth row | 33.0 | 83.5 | 29.2 | 39.4 |
| Select a row | 10.9 | 66.0 | 10.0 | 23.5 |
| Swap two distant rows | 31.0 | 92.1 | 174.9 | 185.5 |
| Create 10,000 rows | 539.3 | 542.3 | 619.3 | 604.5 |

Elements retained reuses row vnodes when item reference and selection are
unchanged. Elements fresh constructs every row on every application observation.
React memoized is the upstream React Hooks adapter; React fresh removes only
the row's `memo` wrapper and comparator. Its header remains memoized. Both
Elements variants use one application observer. These are implementation
comparisons, not identical internal workloads or a general library ranking.

Fresh descriptions increase Elements' partial-update scripting median from
11.8 to 62.1 ms; React's rises from 7.0 to 17.9 ms. Elements' selection scripting
rises from 5.5 to 60.1 ms. The earlier placement optimization still benefits
distant swaps, but avoiding unnecessary DOM moves does not eliminate construction
and traversal costs. Scripting and total medians are calculated separately.

Ten samples per workload, twenty for selection; all retained. Upstream warmups
are three for partial update, five otherwise. Partial update, selection and
swap use 4× CPU slowdown; creation is unthrottled. All four adapters passed
keyed create/remove/swap checks, and the run passed the harness plausibility check.
The historical `_x16` suffix in the partial-update result filename does not
describe this harness revision's actual 4× setting.

## Construction and observation

The separate four-cell diagnostic table measures synchronous JS and DOM work,
excluding subsequent layout and paint. It is unthrottled, with five warmups and
fifteen samples per case. Its medians cannot be compared directly to the table
interaction times above.

| Fresh table size | Construct observation | Construct and update every row |
| --- | ---: | ---: |
| 1,000 rows | 2.9 ms | 8.7 ms |
| 10,000 rows | 39.3 ms | 80.7 ms |

Allocation/GC variability is substantial: the 10,000-row construction samples
range from 25.6 to 120.0 ms. An unminified CPU profile of construction, mounting,
updates and cleanup identifies `markVNode`, `withNamespace`, `normalizeChildren`
and GC as prominent costs. The profile is a source of leads, not a production
CPU percentage breakdown or a measured optimization benefit.

Updating one independent counter took a median 0.011 ms with 1,000 observers
mounted and 0.013 ms with 10,000. Each sample averages 100 synchronous clicks;
these are CPU/DOM costs, not individual input-to-paint latencies. The assertions
verify that the selected counter advances and an unrelated counter stays unchanged.

For one observer projected repeatedly, a parent update selects either one reused
observation or a fresh call at each placement:

| Placements | Reused observation | Fresh calls | Notifications, reused / fresh |
| --- | ---: | ---: | ---: |
| 100 | 0.3 ms | 3.5 ms | 100 / 10,000 |
| 500 | 1.1 ms | 60.0 ms | 500 / 250,000 |

Each fresh selection notifies every projection, yielding P² notifications in
this fixture. Notification counts are instrumented in an extra untimed update.
Reusing one observation avoids redundant selections. This does not imply that
separate observer definitions broadcast to each other.

## Memory and detached projections

Median page-memory estimates in MiB, three samples per cell:

| State | Elements retained | Elements fresh | React memoized | React fresh |
| --- | ---: | ---: | ---: | ---: |
| Ready | 0.64 | 0.64 | 1.18 | 1.18 |
| 1,000 rows mounted | 3.52 | 3.49 | 4.42 | 4.32 |
| After five create/clear cycles | 1.97 | 1.90 | 1.97 | 1.97 |

These use the upstream GC procedure and
[`performance.measureUserAgentSpecificMemory()`](https://web.dev/articles/monitor-total-page-memory-usage),
which estimates page memory beyond the JS heap. No eager-measurement flag was
used. The post-clear values are not back at initial baselines; three samples
and five cycles cannot establish long-term retention behavior. The memory run
passed the harness plausibility check.

A separate targeted lifetime probe retains an authored graph containing 10,000
independent observers, removes its projected DOM, and forces GC across task turns:

- Dropping the DOM reference collects the root and reduces active subscriptions
  from 10,001 to zero. JS heap falls from about 24.9 to 11.9 MiB; the graph is
  deliberately still retained.
- Keeping the detached DOM reference preserves the root and all subscriptions,
  with about 24.9 MiB of JS heap. This supports continued updates/reconnection.

Those are JS-heap measurements from CDP, distinct from the page-memory table.
This probe verifies the tested lifetime relationship, not absence of every leak.

## Startup

Three fresh-browser Lighthouse 13.4.0 runs per adapter, using the harness's
default mobile simulation and an initially empty table. Median milliseconds:

| Audit | Elements retained | React memoized |
| --- | ---: | ---: |
| Script bootup | 23.3 | 66.7 |
| Main-thread work | 161.7 | 220.6 |
| Simulated time to interactive | 1,953.5 | 3,001.6 |

Startup looks favorable here, but three samples are preliminary. React script
bootup ranges from 11.5 to 69.7 ms. Simulated time to interactive includes the
whole page and network model; it is not library execution time. The harness
exposes the same interactive audit twice, so the table shows it once.

The pinned general runner assigns startup zero iterations. `startup.mjs` calls
its existing Lighthouse worker directly, preserves unavailable audits as null,
and uses distinct debugging ports to avoid reusing a browser during shutdown.
The first attempt hit that shutdown race and was discarded; all six reported
samples come from the subsequent complete run.

## Next optimization

Start with vnode construction: investigate consolidating the marker WeakSet
and namespace WeakMap, then reduce temporary arrays in child normalization.
Every helper currently writes both metadata stores. Any consolidation must
preserve explicit namespaces, custom constructors and literal/nested-array
semantics. Benchmark these changes separately before accepting them.

Treat shared-observer notification coalescing as a separate change. Conflicting
observations and reentrant callbacks need defined ordering. Automatically
memoizing observer arguments could change reset/selection semantics and is not
an appropriate shortcut. History snapshots and tick scheduling remain outside
these fixtures.

headless, Node 25.9.0, React 19.2.0. Harness revision:
`3ab4ceaf5591771228f83fb5161b9fda7e15934d`. Interaction/memory execution order was
Elements fresh, Elements retained, React memoized, React fresh. Startup ran
Elements then React. No other benchmark/build/test jobs ran concurrently;
order was not randomized and system noise was uncontrolled. Repeat across
sessions and environments before publishing release claims.
